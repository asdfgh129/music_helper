# 音乐库自检

> 本文负责：自检的完整流程、每个维度「看什么/不看什么」、严重级别与处置、报告怎么读、
> 性能特征、已知局限与误判风险、如何验证自检本身。
> 本文不负责：单条规则的比对公式（见 [rules.md](rules.md)）、流水线各步顺序（见 [workflow.md](workflow.md)）、
> 命令行参数与优先级（见 [usage.md](usage.md)）、阈值与扩展名配置（见 [configuration.md](configuration.md)）。

自检回答一个问题：**这个库现在有哪些文件不符合规范，其中哪些必须人工处理？**

它只有两个入口，判定逻辑完全共用：

| 入口 | 扫描范围 | 是否修复 |
|---|---|---|
| `python main.py --check` | `LIBRARY_DIR` | 默认只报告，`--fix` 才动文件 |
| 主流水线 2.6 步 | `WORKSPACE_DIR`（递归） | 默认修复，`--no-move` 关掉移动 |

两个入口都会先校验目标目录：目录不存在直接报错并以退出码 1 结束。
扫描空目录同样会得到「零问题」的报告，那种报告比报错更难发现。

## 1. 一次自检做什么

```
磁盘
 │  core.scan.scan()          一次遍历；每个文件只打开一次 → Track
 ▼
[Track, ...]
 │  core.check.check_library()
 ├──────────────► CheckResult.findings   6 类问题，每条带 fixable / severe
 ├──────────────► CheckResult.groups     重复组（含 keep / drop）
 │
 ├─► core.report.report_into()  ─► report-*.md + review-*.csv      （只写文件，不动音乐）
 └─► core.check.plan_fixes()    ─► core.ops.Plan ─► execute()      （动文件，进 journal.jsonl）
```

**硬边界：`check_library()` 绝不改文件。** 它只产出「发现」。是否动手由 `plan_fixes()` 决定，
是否真的执行由 `Plan.dry_run` 决定。所以「报告」和「执行」可以分开验证，`--dry-run` 天然成立。

## 2. 六个检查维度

顺序即 `report_into()` 的渲染顺序，也决定了处置优先级。

| # | 类型常量 | 看什么 | 不看什么 |
|---|---|---|---|
| 1 | `文件名格式` | 文件名是否 `歌手 - 歌名.ext`；能否安全规范化，或按标签补全 | 文件名与标签是否一致（第 3 项管） |
| 2 | `标签不完整` | 歌曲名/歌手/专辑/年份/封面 五项是否齐全 | 值是否正确（只有一致性检查会碰这个） |
| 3 | `文件名与标签不一致` | 文件名解析出的歌手/歌名 与 标签是否矛盾 | 谁对谁错（无法判断，一律交人工） |
| 4 | `重复文件` | 标签维度 + 文件名维度，都要求时长差 ≤ `DURATION_TOLERANCE` | 声纹相似度（那是 `soundalike`，独立信号，见 [fingerprint.md](fingerprint.md#8-声纹查重soundalike)） |
| 5 | `缺少歌词` | 同目录同主文件名是否有 `.lrc` | 歌词内容是否为空、是否是纯音乐 |
| 6 | `孤立歌词` | `.lrc` 是否有对应音频 | 歌词归属哪一首 |

第 4 项是唯一产出 `groups`（结构化分组）的维度，其余只产出扁平 `Finding`。
`Finding.track` 指回 `Track`，报告需要读标签/时长时不用二次扫盘。

### 2.1 每个维度考虑了什么

**文件名（1）**：`is_canonical()` 要求同时能解析出歌手、歌名且含 ` - `。
规范化有两条路，优先第一条：

1. `canonicalize()`：只在「恰好一个 `-` 且没有 ` - `」时改写。`AC-DC - Back`、`A-B-C` 一律不动，
   因为多段连字符大概率是名字本身，改成 ` - ` 会把 `AC-DC` 拆坏；
2. `format_filename()`：文件名压根没有歌手结构（例如 `晴天.flac`）时，用标签重写。
   前提是标签齐全且与现有文件名不矛盾——标签自相矛盾时按标签改名，等于把错的那份写到文件名上。

第 2 条受 `rename_by_tags` 控制：`--check --fix` 与主流水线开启，`--only-check-file-name`
关闭（它不读标签，没有可信信息可用）。

**标签完整性（2）**：封面用 `has_cover()` 判断，只认内嵌，不认同目录的 `cover.jpg`。
封面缺失被刻意降级为「提示」，理由见第 4 节。

**一致性（3）**：三个维度都遵循「信息不足就不判」——

| 维度 | 规则 | 为什么 |
|---|---|---|
| 歌手 | 任一侧是占位歌手（`Various Artists`、`群星`、`未知艺人`）→ 跳过 | 合辑里每个文件的标签都是 `Various Artists` |
| 歌手 | token 有交集 → 一致 | `周杰伦 & 方文山` 与 `周杰伦` |
| 歌手 | token 互为子串 → 一致 | `周杰伦` 与 `周杰伦 (Jay Chou)`、`周杰伦 feat. 杨瑞代` |
| 歌手 | 以上都不成立 → 矛盾 | 这是唯一会产生 `severe` 的歌手情形 |
| 歌名 | 去空白、转小写后比较；完全相同或**互为子串**都算一致 | 文件名常带 `(Live)`、`(1)` 等尾巴，标签是干净的 |
| 歌名 | 任一侧为空 → 跳过 | 同上 |

宽松是刻意的：歌手维度判错就是 `severe`，`--fix` 会把文件搬出库；漏判只是少报一条。
代价是 `晴天` 与 `晴天2` 也被视为一致。

**重复（4）**：两个独立信号，取并集。

| 维度 | 键 | 能抓到什么 |
|---|---|---|
| 标签 | `version_key(歌手)` + `version_key(歌名)` | 换格式、换专辑、改名后的同一录音 |
| 文件名 | 去掉下载序号的文件名主干（归一化后） | 标签全空、只靠文件名能识别的同一文件 |

两者都用**时长差 ≤ 3 秒**做二次确认，而不是哈希：同一录音的不同编码哈希必然不同，
而时长几乎一致；反过来时长不同基本可以断定不是同一录音（`Live` 版通常差十几秒）。

版本标记（Live / Remix / 伴奏 / 不插电 / Demo / 翻唱 / feat）在标签维度被保留进键，
所以 `晴天` 与 `晴天 (Live)` 不会被判成同一首。

文件名维度有三个补充规则：

- 比较前去掉空白并转小写，`Artist - Song` 与 `artist - song` 是同一主干；
- `(1)`、`（2）` 与 `_1`、`_2` 都算下载序号（`_n` 是 `Plan` 处理重名的产物，不认它会留下查不出的重复）；
- 文件名没有 ` - ` 时（如 `Intro.flac`）拿不到歌手，**只在同一目录内比对**；
  跨目录同名多半是不同专辑里的不同曲目。

保留策略 `pick_keep()` 按 `(格式优先级, 文件大小)` 取最大值：
`.flac/.dsf > .wav/.ape > .ogg/.opus > .mp3/.m4a > .wma`，同格式取更大者。
**格式优先级高于体积**，所以体积很小的 FLAC 也会赢过体积大的 MP3。

**歌词（5/6）**：只做「同名同目录」的存在性判断，不解析 LRC 内容。
`orphan_lrc()` 按 `config.AUDIO_EXTENSIONS` 判断音频是否存在，所以扩展名集合直接决定
「孤立」的真假——见 [configuration.md](configuration.md)。

**入库判定**不在六个维度里，但共用同一批 `Track`：`readiness_problems()` 要求
歌曲名/歌手/专辑/年份齐全、**年份能解析成 1900–2100 的四位数字**、且文件名与标签不矛盾；
封面和歌词不参与。年份要单独校验，否则会出现「判定可入库、归档却落进 `unknown/`」。

它是 `INCOMPLETE_DIR` 分流的唯一依据，与「标签完整性」不是同一件事：
后者用于报告与 `--fix`，前者只决定去留。

## 3. 严重级别与处置

`severe` 是唯一决定「要不要动文件」的开关。

| 问题 | severe | `--fix` 时的动作 | 目标位置 |
|---|---|---|---|
| 重复文件 | — | `--trash-dup` 回收，否则移走；**「时长未知」的组不动** | `log/_trash/` 或 `<DUPLICATE_DIR>/重复文件/` |
| 歌曲名缺失、歌手缺失 | ✅ | 移动 | `<INCOMPLETE_DIR>/标签不完整/` |
| 文件名与标签矛盾 | ✅ | 移动 | `<INCOMPLETE_DIR>/文件名与标签不一致/` |
| 缺专辑、缺年份、缺封面 | ❌ | 不动，只进报告 | — |
| 文件名不规范 | ❌ | 改名（分隔符规范化，或按标签补全） | 同目录 |
| 缺歌词、孤立歌词 | ❌ | 不动 | — |

`plan_fixes()` 的执行顺序固定为 **先重复 → 再移动 → 最后改名**：

1. 重复优先，因为一个文件可能同时「重复」和「标签不全」，先定归属避免重复处理；
2. 移动其次，因为移动会改变路径，之后不能再按原路径改名；
3. 改名最后，且只对「留在原地」的文件做。

`planned` 集合保证同一个文件在一次计划里只被处理一次。

### 3.1 为什么 `severe` 只有这两类

`--fix` 一旦把「缺封面」「缺专辑」也算进去，一次运行就能把整个库搬进 `INCOMPLETE_DIR`——
库看起来「空了」，而实际上只是缺一张图。所以判定线画在「**没有这首歌的身份信息**」上：
歌曲名和歌手缺失 = 文件不可识别；文件名与标签矛盾 = 身份信息互相冲突。
其余问题都能在不移动文件的前提下修（补标签、补封面）。

### 3.2 为什么「时长未知」的重复不自动处理

读不出时长，通常意味着文件损坏或编码异常。它与同名曲目只是「可能」重复，
而不是「时长一致，确认是同一录音」。这类组只进报告，由人工看一眼再决定。
把它们自动移进 `DUPLICATE_DIR`，等于把「读不出来」当成「确定重复」。

## 4. 报告怎么读

`--check` 产出两份文件到 `--report-dir`（默认 `log/reports/`）：

| 文件 | 内容 | 用途 |
|---|---|---|
| `report-YYYYmmdd_HHMMSS.md` | 汇总计数 + 各类明细表 | 人读，看趋势 |
| `review-YYYYmmdd_HHMMSS.csv` | 类型 / 路径 / 说明 | 交给下一步处理（补标签、人工核对） |

要点：

- 汇总里每个类型都会出现，**数量为 0 也出现**——「0」本身就是结论，不要当成缺项；
- `重复文件` 的计数是**待处理文件数**，不是重复组数；一组的「保留」文件不计入；
- 明细一律带完整路径：跨年代目录同名时，只有文件名不足以定位；
- Markdown 正文每类最多列 `MAX_TABLE_ROWS`（200）行，超出部分只在 CSV 里，避免大库生成巨型表格；
- 报告只描述检查结果，**不代替** `log/journal.jsonl` 的动作流水。想知道「文件去哪了」看 journal。

## 5. 关键点（改代码前必须知道）

1. **判定只在一处实现**：命名 `core/naming.py`、标签 `core/tags.py`、重复 `core/dedupe.py`、
   歌词 `core/lyrics.py`、入库 `core/check.py: readiness_problems()`。
   在 `main.py` 里再写一套是明确禁止的，历史上就是这么产生四份互相矛盾的实现的。
2. **检查阶段不产生副作用**：不 `os.remove`、不 `shutil.move`、不发网络请求。
   需要动文件时只能往 `Plan` 里加操作。
3. **`severe` 是唯一的移动开关**。新增检查项时默认 `severe=False`，
   想让文件被移走必须明确论证「身份信息不可用」。
4. **改名撞车必须失败**：`Plan` 不会为 `rename` 加 `_1` 后缀。静默加后缀会造出一个
   「看起来正常、实际是重复」的文件，而它又不在查重规则里。
5. **`--limit` 会破坏重复判定**：它按路径前缀切片，同一组的另一半可能被切掉，
   于是「重复」凭空消失。只用于调试，不要用它评估库的健康度。
6. **缺 `mutagen` 时全部文件都会被判为标签缺失**：`read_meta()` 静默返回空值，
   自检不会报错，只会把整个库判进 `INCOMPLETE_DIR`。跑之前先确认
   `python -c "from core.tags import MUTAGEN_AVAILABLE; print(MUTAGEN_AVAILABLE)"`。
7. **结果目录不能嵌套在被扫目录里**：`DUPLICATE_DIR`、`INCOMPLETE_DIR` 若在 `LIBRARY_DIR`
   或 `WORKSPACE_DIR` 内，会被当成普通音频反复检查、反复搬运。
8. **`--check` 发现问题的退出码仍是 0**：只有目录不存在或外部工具失败才非 0。
   想拿它做 CI 门禁，需要自己解析 CSV 或报告。
9. **月份参数不筛选自检**：`--month` 只影响解密与拷贝，自检始终是整库。

## 6. 性能特征

自检的成本几乎全在「打开文件读元信息」，不在比对。

| 环节 | 复杂度 | 说明 |
|---|---|---|
| `scan()` | O(文件数) 次磁盘遍历 | 一次 `os.walk` 建完索引，后续全在内存 |
| 读标签 + 时长 + 封面 | **每文件 1 次打开** | `core/tags.read_meta()` 一次读完三件事 |
| `find_by_tag` / `find_by_filename` | O(n log n) | 哈希分桶 + 桶内按时长排序 |
| `missing_lrc` | O(n) 次 `os.path.exists` | |
| `orphan_lrc` | O(目录数 × 目录内文件) | 传入目录列表时按目录递归遍历 |
| 报告渲染 | O(明细数)，正文截断到 200 行/类 | |

`--only-check-file-name` 完全不读标签（`scan(with_tags=False)`），也不做封面探测，
在只关心文件名时是最快的入口。

## 7. 已知局限与误判风险

这些是**当前实现的真实行为**，判断报告时要心里有数。

| 场景 | 表现 | 影响 |
|---|---|---|
| 文件名用中文、标签用拉丁名（`周杰伦` vs `Jay Chou`） | 无交集也无子串 → 判「歌手矛盾」 | 跨语言别名无法自动判断，只能人工处理 |
| 标签本身错了，但和文件名"错得一致" | 检查通过 | 自检验证的是「文件名与标签是否打架」，不验证「标签是否真的对」——那要靠声纹与在线匹配 |
| 库用文件夹级封面（`cover.jpg`），音频没有内嵌图 | 恒报「缺封面」 | 设计如此：补封面写的是内嵌图，判定也看同一个位置 |
| 裸 `.aac`（ADTS 流） | 不在 `AUDIO_EXTENSIONS` 内，完全不可见 | 其同名 `.lrc` 会被判为孤立歌词 |
| 两个都是规范名、同名且时长接近的不同录音 | 文件名维度判为重复 | 跨目录比对是放开的有意行为，误判时靠 `DUPLICATE_DIR` 兜底 |
| 大小写不同的同名文件（跨目录） | 已归一化，会判为重复 | 与 Windows 不区分大小写的实际行为一致 |
| 跨盘移动被 Ctrl-C 打断 | 目标目录可能留下 `xxx.flac.part` | `.part` 不是音频扩展名，不会被扫描；确认后手工删掉即可 |
| `LIBRARY_DIR` 配错 | 现在会直接报错退出 1 | 不再出现「假全绿」报告 |

## 8. 怎么验证自检本身

自检是「判官」，判官自己也会错，所以改完必须验证：

```bash
python -m pytest -q                                  # 全量测试
python -c "from core.tags import MUTAGEN_AVAILABLE; print(MUTAGEN_AVAILABLE)"
python main.py --check --dry-run                     # 只出报告与计划，不动文件
```

- 先跑 `--check --dry-run`，把 `review-*.csv` 抽 10 条打开文件核对，
  确认「报告说的」和「耳朵听到的」一致，再考虑 `--fix`；
- 大批量修复前用 `--limit 20` 小样本试跑（注意：`--limit` 会破坏重复判定的完整性）；
- 改动任何判定规则后，必须同步 `tests/` 用例——`tests/test_check.py` 覆盖入库判定与一致性，
  `tests/test_dedupe.py` 覆盖重复判定，`tests/test_naming.py` 覆盖文件名规则，
  `tests/test_tags.py` 覆盖标签读取与格式注册；
- 报告数量异常（例如「缺封面」突然等于总文件数）优先怀疑依赖缺失或扩展名集合，
  而不是库真的坏了。

## 9. 扩展一项检查

步骤见 [architecture.md](architecture.md#6-扩展指南)，落到自检有四个固定动作：

1. `core/check.py` 加 `KIND_*` 常量；
2. `check_library()` 里产出 `Finding`，默认 `severe=False`；
3. `report_into()` 的渲染顺序里加进去（顺序变了要同步本文第 2 节）；
4. 需要修复则在 `plan_fixes()` 加分支，保持「先重复、后移动、最后改名」的顺序。

最后同步 [rules.md](rules.md) 与 `CHANGELOG.md`。
